# 실제 문서 검출 정확도 평가

평가일: 2026-11-11. 범위는 기존 실제 XLSX·DOCX 한 쌍과 그 복사본이다. 이 결과는 모든 재무 문서에 대한 일반적인 정확도가 아니다.

## 1. 변경 전 실제 샘플 측정

원본을 다시 파싱한 결과는 이전 품질 분석과 같았다. 253건(CROSS 188, CALC 14, PLAN 51, ALLOC 0), 확인 필요 142건과 보류 111건이다. 사용자 승인 전 확정 오류·통과는 모두 0건이며, 우선 7·추가 21·상세 225건을 유지한다. 이번 작업으로 후보를 삭제하거나 검증을 생략하지 않았다.

| 실제 문서에서 확인한 사실                             | 평가                                                                                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 총자산·총부채·순자산 각 문서의 합계, Excel 월 잉여금  | 구성 근거가 확보된 계산 7건은 보고값과 재계산값이 일치했다. 확인된 계산 오류는 0건이다. 전체 계산이 정상이라는 뜻은 아니다.                            |
| 신용대출 금리                                         | Excel 7.5%, Word 6.5%로 원문 숫자 차이 1.0%p를 확인했다.                                                                                               |
| 학자금대출 잔액                                       | Excel 700만 원, Word 701.5만 원으로 15,000원 차이를 확인했다.                                                                                          |
| 신용대출 잔액·총자산·총부채·순자산·월 잉여금          | 각각 79,000원·10,200,000원·94,000원·10,106,000원·23,980원 차이가 있는 원문을 확인했다.                                                                 |
| 위 7개 독립 수치 발견                                 | 숫자가 다르다는 사실과 동일 기준의 오류라는 판정은 별개다. 기준일·시나리오·대상 확인 전에는 확정 오류가 아니다.                                        |
| 개별 금액과 묶음 금액, 보유액과 납입액, 상환방식 코드 | 기존에 잘못 연결했던 59건은 제외 기록으로 유지한다. 정상인 관계를 오류로 확정하지 않는다.                                                              |

모든 253건을 사람이 정답으로 라벨링한 평가는 아니다. 따라서 이 원본 전체에 대한 정밀도·재현율을 임의로 산출하지 않는다. 상세 원인과 원본 공유 집계는 [9차 품질 분석](result-quality-analysis.md)에 남아 있다.

## 2. 오류 주입 방법과 보존 검증

`tests/accuracy-files.ts`가 원본 ZIP을 메모리로 복사하고 별도 평가 시트와 Word 부록만 추가한다. 기존 시트·표·문단·병합·수식·본문 순서를 유지하며, Word의 마지막 섹션 설정 뒤에 내용을 넣지 않는다. 각 오류는 별도의 복사본이다. 정상 대조본은 같은 부록에서 문제값 또는 행동 하나를 수정한다. 원본 문서는 덮어쓰지 않는다.

테스트는 실제 `parseXlsx`·`parseDocx` → 정규화 → 계획 추출 → 추천 → `inspectDocuments` 경로를 거친다. 승인 전에는 입력 확인 상태를 변경하지 않는다. 승인 후 평가에서는 원문을 보고 사용자가 입력하는 조건을 테스트가 명시적으로 재현한다. 미확인 지원금의 금액·단위도 원문에서 선택한다. 자동 추출된 것처럼 가장하지 않는다.

기존 모든 worksheet XML의 동일성, 기존 DOCX 파싱 블록의 동일성, 원본 파일의 SHA-256 동일성을 검사한다. 오류·정상 대조본은 실행 중 생성되며 실제 금융 문서 사본을 저장소에 포함하지 않는다. 기대 금액과 평가용 문구는 테스트에만 존재한다.

## 3. 오류별 결과

자동 발견 성공은 **주입한 관계에서 기대한 수치 차이를 산출하거나, 필요한 조건을 갖춘 구체적 충돌을 특정한 경우**다. ‘관계를 확인하세요’라는 일반 후보는 성공으로 세지 않는다. 승인 후 성공은 원문 조건을 수동 확인한 뒤 기존 엔진이 기대한 오류를 판정한 경우다.

| 독립 오류      | 기대 결과                                          | 자동 발견                                                 | 사용자 확인 후 실제 결과                                   | 정상·수정 대조본                  | 원본 위치                    |
| -------------- | -------------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------- | ---------------------------- |
| CALC 월 잉여금 | 315 − 271 − 35 = 9만 원, 보고 7만 원과 2만 원 차이 | 성공: 차이 후보                                           | 오류. 보고 70,000원, 계산 90,000원, 보고−계산 = −20,000원  | 보고 9만 원이면 통과              | 평가 시트의 각 셀·원문 보존  |
| CROSS 총자산   | 3,090만 원과 3,070만 원의 20만 원 차이             | 성공: 차이 후보                                           | 오류. Excel−Word = 200,000원                               | 두 값 3,090만 원이면 통과         | Excel 셀, Word 표 행·열 보존 |
| ALLOC 예금     | 보유 590만 원, 동시 배정 890만 원, 초과 300만 원   | 실패: 기간·현재 자산 구분 등이 비어 일반 확인 후보만 생성 | 오류. 실제 8,900,000원, 가용 5,900,000원, 초과 3,000,000원 | 두 번째 배정 0원이면 이 규칙 통과 | 자산·목표 셀, 배정 문단 보존 |
| PLAN 지원금    | 미승인·미수령 132만 원의 현재 확정 자산 선반영     | 실패: 금액·승인·수령·반영처 등 구조화 부족                | 오류. 1,320,000원 선반영                                   | 별도 예상 시나리오이면 통과       | 지원금 원문 문단 보존        |
| PLAN 제안·실행 | 동일 ETF·동일 기간의 중단과 유지                   | 실패: 대상·기간·시나리오 구조화 부족                      | 오류. 동일 대상의 중단·유지 충돌                           | 두 행동 모두 중단이면 통과        | 두 원문 문단 보존            |

지원금 문장에는 날짜가 있다. 기존 범위 감지 정규식이 날짜의 하이픈을 금액 범위로 볼 수 있어, 자동 후보의 금액이 비었다. 이 실패를 감추지 않고 사용자 금액·단위 확인을 거쳐 평가했다. 이번 작업에서는 계획 추출이나 검증 규칙을 새로 추가하지 않았다.

- 구체적 자동 발견: **2/5 = 40%**, 자동 미탐 **3/5**. 일반 확인 후보 자체는 5개 모두 존재하지만 검출 성공률의 분자에 넣지 않는다.
- 필요한 원문 확인·구조화를 완료한 후 오류 판정: **5/5 = 100%**, 이 조건에서 최종 미탐 0건.
- 오류를 수정한 정상 대조 관계: **5/5 통과**, 구체적 자동 오탐 및 확정 오류 오탐 **0/5**.
- 기준일이 다르거나 시나리오가 다른 총자산 대조: **2/2 확인 필요**, 확정 오류 0건. 다른 조건을 강제로 같은 값으로 덮어쓰지 않았다.
- 모든 측정 관계에 원본 위치·원문이 남아 있다.

주의: 복사본에는 원래 문서의 내용도 남아 있다. 위 점수는 평가 부록의 지정 관계만 채점한 값이다. 기존 문서에서 파생되는 다른 후보를 모두 정상 또는 오류로 채점한 수치가 아니며, 본문 후보는 앱에 그대로 남는다. ‘정상 대조본’도 평가 대상 관계의 정상 조건을 뜻한다.

## 4. 사용자 조작 수와 재사용

실제 Chrome에서 클릭·선택·필드 입력 한 번을 각각 1회로 셌다. 파일 업로드와 검사 시작은 공통 준비이며 제외한다. 근거 펼치기와 스크롤도 제외한다. 아래 첫 확인 수치는 자동 발견 이후의 경로이며, 특히 CROSS는 대상 결과 탐색·필터 조작을 제외한 해당 카드의 확인 수다. 나머지 경로는 필요한 화면 이동을 포함한다. 서로 다른 경로의 숫자를 그대로 난이도 순위로 해석하지 않는다.

| 경로                                   | 이번 Chrome 측정 | 기존 대비                                                                                   |
| -------------------------------------- | ---------------: | ------------------------------------------------------------------------------------------- |
| CALC 구성 근거 열기 → 범위 확인 → 승인 |              3회 | 동일                                                                                        |
| CROSS 결과 열기 → 예 → 적용            |              3회 | 동일                                                                                        |
| 동일 CROSS 관계 재검토                 |              2회 | 이전 소스상 3회에서 예 재선택 1회 감소. 기존 승인 상태를 유지하며 적용은 명시적으로 누른다. |
| ALLOC 자산·목표 확인 및 배정 수동 입력 |             37회 | 복잡한 고급 편집 경로는 그대로다. 아직 최소 조작 경로라고 주장하지 않는다.                  |
| PLAN 지원금 조건 확인                  |             13회 | 금액·단위 선택 및 승인·수령·반영일 등 수동 구조화가 여전히 필요하다.                        |
| PLAN 제안·실행 조건 확인               |             19회 | 두 문장의 대상·금액·기간·시나리오를 수동 확인한다.                                          |

이전 경로의 숫자는 기존 UI 코드 및 해당 E2E 순서와 비교한 값이고, 이전 버전을 다시 브라우저에서 계측한 기록은 아니다. 새 측정은 `e2e/accuracy.spec.ts`의 콘솔·테스트 주석으로 재현한다. 신규 승인과 실제 승인 재사용을 구분하며, 추출 신뢰도나 다른 원본 위치를 근거로 승인을 확장하지 않는다. 수정·제외·원문 변경·파일 교체 후에는 이전 승인을 재사용하지 않는다. 다른 규칙이 같은 확인 항목을 사용하더라도 계산 범위·새 관계의 승인까지 자동 부여하지 않는다.

## 5. 화면 변경

기본 화면은 ‘우선 확인할 문제’와 확정 오류 수를 먼저 보여준다. ‘추가 확인’은 조건이 모호한 후보를 접어서 제공한다. 253건 전체 분석 수, 반복 기록 수, 공유 근거 설명은 접힌 상세 기록·판단 근거에 둔다. 원본과 기존 상세 편집, 고급 규칙 설정은 유지한다. 첫 등록 화면의 개인정보 안내를 짧게 하고 상세 검토 버튼에서 전체 후보 수를 제거했다. 우선 결과 제목·본문 크기와 대비를 정리했다.

이미 승인한 동일 원본 쌍을 열면 기존 ‘예’ 답변을 유지한다. 적용 버튼을 누르지 않고 새 승인이나 상태 변경을 만들지 않는다. 자동 후보에는 선택값을 미리 부여하지 않는다. 모름·다른 조건은 기존 승인 해제 경로를 사용한다.

## 6. 재현과 변경 파일

README의 두 실제 파일 환경변수를 설정하고 다음을 실행한다.

```powershell
$env:PLANCHECK_ACCURACY_EXPORT='1'
npm.cmd test -- tests/accuracy.test.ts
npm.cmd run build
npm.cmd run test:e2e
npm.cmd run lint
npm.cmd run format:check
```

선택한 내보내기 환경변수는 `test-results/accuracy-evaluation.json`과 `test-results/accuracy-fixtures/`에 비공개 복사본 10쌍을 만든다. 원문 금융 내용이 포함되므로 이 폴더는 Git 제외 대상이다. Chrome E2E가 `test-results`를 초기화하므로 보관하려면 E2E 후 평가 테스트를 다시 실행한다. 경로를 지정하지 않으면 실제 문서 테스트를 건너뛰며 실제 평가 성공으로 보고하지 않는다.

- 평가: `tests/accuracy-files.ts`, `tests/accuracy.test.ts`, `e2e/accuracy.spec.ts`
- 승인 재사용·안전성: `src/inspection/review.ts`, `tests/review-reuse.test.tsx`, `src/components/InlineReview.tsx`
- 화면: `src/App.tsx`, `src/components/InspectionResults.tsx`, `src/components/PlanningEditor.tsx`, `src/index.css`
- 회귀·문서: `e2e/inline-review.spec.ts`, `e2e/result-quality.spec.ts`, `vite.config.ts`, `README.md`, 이 문서

대용량 문서 복사·파싱 평가와 UI 테스트가 서로 경합하지 않도록 Vitest 작업자를 1개로 제한했다. 기존 대기 시간·판정 기대값을 완화하거나 테스트를 삭제하지 않았다.

기존 검수 회귀 테스트는 업로드 완료 순서에 따라 Word의 320을 다시 320으로 입력할 수 있었다. 숫자가 실제로 변경되는 Excel 항목을 명시적으로 선택하도록 수정했으며, 수정 후 승인 해제 기대값은 그대로 유지했다. Windows 자식 테스트 프로세스 시작 제한 때문에 실패한 실행은 성공으로 기록하지 않고, 실행 권한을 조정해 전체 테스트를 다시 검증했다.

최종 검증: 기존 151개를 포함한 Vitest **164/164 통과**, 기존 7개와 신규 5개를 합친 Chrome E2E **12/12 통과**. 프로덕션 빌드·서식 검사·린트가 통과했다. 린트에는 기존 TanStack Table의 React Compiler 호환성 경고 1건이 남아 있다. 기존 파서·정규화 및 CALC·CROSS·ALLOC·PLAN 엔진 파일은 변경하지 않았다.

## 7. 남은 한계와 다음 권장 작업

조건부 금액·배정·계획은 원문에 조건이 있어도 구조화가 충분하지 않다. 따라서 자동 검사기로서의 완전한 검출률은 아직 낮다. 특히 37회 배정 입력은 첫 사용자에게 부담스럽다. 원본 전체 정답 라벨링, 추가 문서 쌍, 다른 표현·숫자를 사용한 블라인드 평가가 필요하다. 40%·100%는 5개 통제 사례의 결과일 뿐 서비스 전체 성능이 아니다.

다음 단계에서는 새 규칙보다 날짜와 금액 범위의 구분, 기존 계획 후보의 필수 조건 입력 경로를 좁히는 개선을 우선 권장한다. 자동 추측으로 사용자 승인을 대체해서는 안 된다.
